# Testing Kage

128 Rust tests and 11 TypeScript tests; 5 of them reach live Zcash testnet. Run the Rust ones one crate at a time (the Zcash crates are large; this keeps memory low):

```sh
cargo test -p spendguard -p x402z-protocol -p x402z-server
cargo test -p x402z-agent
cargo test -p x402z-mcp
cargo test -p x402z-facilitator          # includes the live testnet tests (network needed)
cargo build -p x402z-server -p x402z-facilitator --bins --examples && (cd packages/x402-zcash && npm test)
```

All 137 passed on 2026-10-23 (macOS, Rust 1.89.0, Node 26); the 2 resource-URL tests added to `x402z-server` on 2026-10-24 passed with its other 40 that day. CI (`.github/workflows/ci.yml`) runs them in four jobs: the fast crates; the facilitator's in-process real-transaction tests, which do Halo2 proving; the live testnet tests; and the TypeScript package against the built binaries.

The browser E2E suite (Playwright in headless Google Chrome, `e2e/`) is separate: `e2e/stack.sh` starts the real stack on 127.0.0.1 and `npm run test:e2e` runs 32 specs at 1280 px and at 375 px (64 runs, one mobile-only spec skipped on desktop). Last run 2026-10-25: **63 passed, 0 failed, 1 skipped**, with no retries. The stack and Chrome ran under the shared heavy slot; the stack was stopped and the slot released afterward.

## What is not a chain test, and why

- **Server `X-PAYMENT` / `/api/redeem` tests** run against a small in-process HTTP stand-in for *our own* facilitator's `/settle` (it checks the bearer token). The stand-in answers in the facilitator's wire format and signs receipts with the test key. It exists to test the server's handling of each facilitator answer. The facilitator's actual chain checks are covered by `verify_real_tx` (in-process transactions) and `live_testnet` (real chain). The same server path ran live on testnet: see the next section.
- **The agent's race, lost-answer and preflight tests** use localhost HTTP servers in the x402 wire format. The race tests write the competing call's payment into the ledger (or tab file) while the server answers, which is the moment the old code was exposed; no transaction is built (there is no seed), so nothing touches a chain.
- **The MCP tests** use localhost HTTP fixtures that return a fixed x402 402 (with a tab offer), or answer `X-PAYMENT` pending and then 200 for the resume test, whose ledger is seeded with the state right after a broadcast. Every `paid_fetch` and `tab_fetch` there is refused by spendguard or by the missing wallet before any chain work, so nothing touches a chain. The paying path ran live: see the next section.
- **The broadcast-outcome tests** call `record_broadcast` with each outcome instead of a real `SendTransaction` failure; the split between creating and broadcasting the transaction is what they pin down.
- **The agent's Tab client test** runs against a localhost issuer that speaks the server's tab wire format with real blind RSA; the txid it redeems is never looked up. The same client ran against the real server and testnet: see the next section.
