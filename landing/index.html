Private payments for AI agents.

Your agent pays for APIs in shielded Zcash, inside a spend policy you write in code. Merchants check each payment with a viewing key that can't spend a coin. Nobody on chain learns who paid whom, or how much.

Key custodywho holds what ↓

The kage CLI ships with the package. A new wallet's seed goes to a 0600 file; the facilitator only ever gets the merchant's incoming viewing key, and keys check tells you which kind of key you're holding before you hand it out.

How a payment works

Four checks between an agent and its wallet.

It speaks the x402 wire format (402 → pay → X-PAYMENT → 200), so it fits the agent-payments stack that already exists, with Zcash's privacy underneath.

The policy runs before the wallet

Cap, allowlist and approval are checked inside the engine, under a file lock, before a transaction exists. A host off the list never even gets the request.

Shielded on chain

The agent pays from its own shielded wallet with the 402's nonce in the encrypted memo. The explorer shows a transaction, and nothing about it.

tx401cad2c…77fa ↗ amount memo from to

Merchants hold a viewing key, not a spend key

The facilitator trial-decrypts the payment with the merchant's incoming viewing key, checks amount and memo, and signs a receipt. It can't spend, and can't see what the merchant sends.

X-PAYMENT-RESPONSE, decoded
{"success":true, "transaction":"<txid>", "network":"zcash-testnet", "payer":""}
payer is always "": nobody, the merchant included, learns the payer's address.

An LLM can't approve its own payment

At or above the threshold, onApproval decides. Approvals reach the engine over a per-process secret, so the model driving the agent never holds it.

reference / keys

Keys: who holds what#

Every key has one holder and one job. The merchant's server and facilitator never hold anything that can move money.

KeyHeld byCan
Agent seed (spending key)the agent, from your secret storespend the agent's wallet, nothing else
Merchant seedoffline, never on a serverspend the merchant's income
Merchant UIVK (incoming viewing key)the facilitatorsee payments received: amount and memo. Can't spend, can't see what the merchant sends
UFVK (full viewing key)nobodywould also reveal outgoing payments; Kage refuses it (assertIncomingOnly)
A viewing key can't be revoked once shared: treat it as permanent read access to incoming payments, and move to a new account if it leaks.
reference / spend policy

Spend policy#

The policy runs inside the engine, under a file lock, before a transaction exists. Every decision lands in a ledger sealed at rest (kage.ledger()).

FieldTypeMeaning
dailyCap"0.008 ZEC" or zat bigintmost the agent spends per UTC day, counting every broadcast payment (an unknown broadcast outcome counts too)
allowedHostsstring[]hosts it may pay: api.example.com, *.example.com, 127.0.0.1:4300. Checked before the first request
approvalThresholdZEC, optionalat or above this, onApproval decides. No handler = refused
allowInsecureHttpbooleanplain http beyond loopback (default off)

reference / facilitator

Facilitator API#

Runs next to your API with the merchant's incoming viewing key. Follows the coinbase/x402 v1 facilitator endpoints, with a zcash-shielded scheme.

GET/supportedpublic

Returns {kinds: [{x402Version: 1, scheme: "zcash-shielded", network: "zcash-testnet"}]}.

POST/verifybearer token

Read-only check of {x402Version, paymentPayload, paymentRequirements}; returns {isValid, invalidReason, payer}.

POST/settlebearer token

Binds the requirement (nonce, payTo, amount) to the txid and returns the settlement fields plus an ed25519 receipt. The paywall trusts only receipts signed by its configured key.

GET/healthpublic

lightwalletd reachability, cached for 5 s. Point your monitoring here.

ship it / production

Production checklist#

  • The protocol is network-agnostic; this release is wired to testnet only.
  • Use an Orchard/Ironwood-only UIVK for the facilitator; keep the merchant seed offline.
  • Load the agent seed from a secret manager; set ledgerKey explicitly and back up wallet.dir.
  • Give the paywall a durable challenge store (store) when you run more than one process.
  • Run the facilitator next to your API with its bearer token; expose /health to monitoring.
  • Expect about 75 s per payment (one block). For many small calls, a Kage Tab buys N unlinkable tokens with one payment.
