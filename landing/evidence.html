The spec, the runs, the evidence.

Kage lets AI agents pay for APIs in the x402 v1 wire format, settled as Zcash shielded testnet transactions. spendguard checks every payment before a transaction exists. The merchant's facilitator verifies it with an incoming viewing key alone: no spend key, no view of the merchant's own spends.

docs / overview

Overview#

An agent asks for a paid resource and gets 402 Payment Required with a Zcash option in accepts[]. It pays the merchant's shielded address with the challenge's nonce in the encrypted memo, then retries with X-PAYMENT naming the txid. The chain shows neither the amount, the memo nor either party.

Client agent or any wallet

holds
its own spending key, the spendguard policy and ledger
never
the merchant's keys

Resource server x402z-server

holds
the merchant's shielded UA, the receipt public key, a SQLite challenge book
never
any Zcash key

Facilitator x402z-facilitator

holds
the merchant's unified incoming viewing key (UIVK), an ed25519 receipt key
never
a spending key or a full viewing key

lightwalletd testnet.zec.rocks

holds
the public chain
never
anything shielded

Prior art. coinbase/x402 v1 defines the 402 body, X-PAYMENT and the facilitator endpoints for EVM payments; Kage keeps that wire format and adds a zcash-shielded scheme. A Zcash Community Grants application, "Shielded x402" (forum topic 57826, posted 2026-09-25 by the forum user baby-zack-agent), proposed private machine payments over x402 and was rejected on 2026-09-28. That application is another applicant's: Kage is a separate build by Nivesh Gajengi and shares none of its code. Kage adds a facilitator that holds only the incoming viewing key, spendguard before the wallet, Kage Tab blind-RSA batching, and ten live testnet payments anyone can check.

Quickstart#

Building on Kage? npm install kage-x402 and the 10-line agent are on the landing page. This page is the protocol underneath: a Rust workspace pinned to toolchain 1.89.0. Run the tests one crate at a time; the Zcash crates are large.

shell
cargo test -p spendguard -p x402z-protocol -p x402z-server   # 16 + 14 + 44
cargo test -p x402z-agent                                      # 32
cargo test -p x402z-mcp                                        # 8, drives the binary over stdio
cargo test -p x402z-facilitator                                # 17: 6 build Halo2 proofs, 3 hit testnet
cd packages/kage && npm run build && npm test                  # 19: TypeScript, 10 hit the engine and testnet

Nothing is mocked. Without a key, a wallet or funds, each binary stops with a readable error and a non-zero exit code:

After a cargo build, cd e2e && npm ci && npm run stack runs the whole stack locally with the published demo UIVK and no wallet (dashboard on 127.0.0.1:4120; npm run test:e2e then drives it in Google Chrome), then pay the QR from any testnet wallet. A paid agent run needs a funded testnet wallet for the agent, a merchant UA and UIVK, a receipt key pair from x402z-facilitator keygen and a shared X402Z_FACILITATOR_TOKEN. The README walks through it; x402z-server serves the paid API on 127.0.0.1:4020 and the dashboard on a separate loopback port, 127.0.0.1:4029.

protocol / payment required

The 402#

The body follows coinbase/x402 v1: {x402Version: 1, accepts: [PaymentRequirements], error}. The Zcash entry:

FieldValueNotes
scheme / networkzcash-shielded / zcash-testnetMainnet challenges are refused by the protocol crate.
maxAmountRequiredzatoshi, as a string1 ZEC = 108 zat. The demo price is 100,000 zat.
payTounified addressShielded receivers only. A UA with a transparent receiver is refused.
extra.memoNoncex402z-<24 hex>Single use. Goes into the payment's encrypted memo as text.
extra.expiresAtUnix secondsmaxTimeoutSeconds is 900. Persisted in SQLite, so a restart keeps it.
extra.paymentUriZIP 321 URIFor any wallet; see ZIP 321.
extra.taboptionalThe Kage Tab offer.

Each client IP gets a token bucket of X402Z_CHALLENGE_RATE_PER_MIN challenges and redeem attempts (default 30). Over it: 429 with Retry-After.

protocol / client policy

spendguard#

The agent checks every payment before it touches the wallet. Rules run in order, and the first denial wins:

  1. Host allowlist. Deny by default. Exact host or *.suffix; *.data.test matches x.data.test, not evildata.test. An entry with a port (127.0.0.1:4020) or a scheme (https://…) allows only that. Checked before the agent's first request, with plain HTTP to a non-loopback host refused.
  2. Amount > 0.
  3. Daily cap per agent and UTC day, inclusive, with checked arithmetic: an overflow is a denial.
  4. Approval threshold, inclusive. The CLI asks the operator; the MCP server always declines.

A denied payment builds no transaction. Two agent runs at once take turns on a file lock, so they can't both pass the cap: a test runs six at once against room for one payment, and exactly one pays.

protocol / retry

X-PAYMENT#

The client retries with X-PAYMENT: base64(json). The payload names the challenge as well as the txid, because a shielded transaction gives the server nothing to look up. The facilitator then has to find that same nonce inside the encrypted memo, so a payment can't be pointed at another challenge.

X-PAYMENT, decoded
{ "x402Version": 1, "scheme": "zcash-shielded", "network": "zcash-testnet",
  "payload": { "txid": "<64 hex>", "memoNonce": "x402z-…" } }

Wallets that can't set headers use POST /api/redeem {memoNonce, txid}. It runs the same checks.

protocol / verification

Facilitator#

GET /supported, POST /verify (read-only), POST /settle and GET /health. For each payment it:

  1. fetches the transaction with lightwalletd GetTransaction and checks its txid;
  2. parses it at the consensus branch of its mined height;
  3. trial-decrypts every Sapling, Orchard and Ironwood output with the merchant UIVK;
  4. sums the outputs whose memo is the nonce and whose recipient is the matching payTo receiver;
  5. reads the mined block's header time and checks it against expiresAt plus a 1,200 s grace.
Least privilege, tested. A test builds the merchant's own change and outgoing outputs with the open nonce in every memo. The full viewing key sees all four outputs; the UIVK sees none, so none can be credited.

It refuses: no matching output, a wrong or sibling diversified recipient, underpaid, mined after expiry plus grace, a foreign payTo, a payTo with a transparent receiver, and a nonce already bound to another txid (kept in SQLite across restarts). It then signs an ed25519 receipt: base64url(claims) "." base64url(sig) with minedAt from the block header.

protocol / response

Settlement#

The server checks the receipt against X402Z_RECEIPT_PUBKEY and the stored challenge, burns the nonce once in SQLite, and answers:

OutcomeStatusX-PAYMENT-RESPONSE
Paid200{success: true, transaction, network, payer: ""}
Not confirmed yet402settlement_pending, the same challenge, nothing burned
Refused402invalid_payment, payment_expired, nonce_already_used, unknown_challenge, invalid_payload, invalid_network, invalid_scheme; a fresh challenge
Facilitator down502facilitator_error, nothing burned

Testnet blocks come about every 75 s, sometimes much slower. The default is one confirmation, and the agent retries every 15 s for up to 900 s.

Any wallet (ZIP 321)#

extra.paymentUri is a ZIP 321 URI. librustzcash's own parser reads it back to the same address, amount and memo. The dashboard's 402 card renders its QR locally at /api/challenge/{nonce}/qr.svg, with copy, Open in wallet and a paste txid box that answers paid, pending (re-checked every 15 s) or refused.

surfaces / batching

Kage Tab#

One shielded payment buys N tokens, each spent on one later request with X-PAYMENT scheme zcash-shielded-tab. The server can't link a token to the payment or to its siblings: RFC 9474 blind RSA (RSABSSA-SHA384-PSS-Randomized, RSA-2048), with a SQLite spent set.

The agent side: x402z-agent tab-buy <n> pays from the agent's wallet, or tab-buy <n> --external prints a ZIP 321 request for any wallet followed by tab-redeem <txid>. Then tab-fetch spends one token per request; the MCP tool tab_fetch does the same, and an LLM bought and spent a tab with it on Oct 22. Spendguard checks the whole tab price before anything is paid, and the agent refuses a different key from the same server within one key epoch.

Limits. A token hides only among the tokens issued under the same key (7-day epochs by default), and only if the merchant gives every buyer that same key; spending them in a burst links them by time. The runs used one machine. Those two tabs were paid from a zingo-cli demo wallet through --external; the third (Oct 22) from the agent's own wallet. Tokens are bearer secrets, sealed on disk with the ledger key.
trust / limits

What still leaks#

  • The client's IP reaches the merchant. The paid request is ordinary HTTP; use Tor or a proxy if it matters.
  • lightwalletd sees which txid is looked up, and when.
  • X-PAYMENT is a bearer credential: whoever presents a paid (nonce, txid) first gets the content, and the server serves the same pair again for 10 minutes so a lost 200 is not a refusal. The server's feed lives on a loopback admin port that answers only to its own Host, and shows only a nonce prefix next to a txid.
  • Kage Tab unlinkability assumes one key per epoch for every buyer; the agent pins the key it saw, but can't see what other buyers got.
  • The agent ledger and tab tokens are sealed at rest (XChaCha20-Poly1305); anyone with the ledger key or the agent seed can read them.
  • Timing. The 402 and the next block can be linked by time, even though the transaction reveals nothing.

Also: testnet only, pre-release librustzcash crates (NU7 is live on testnet), not audited.

trust / tests

Tests#

150 tests: 131 in Rust, 19 in TypeScript. Six build in-process transactions with real keys, real note encryption and real Halo2 proofs for the Orchard/Ironwood parts (Sapling outputs use sapling-crypto's mock proof bytes); those are not broadcast. Thirteen reach live testnet: three verify the ten real payments with only the UIVK, eight drive the kage-x402 SDK against the real engine with wallets synced through lightwalletd, and two run the TypeScript client and middleware against the real binaries and testnet. A Playwright suite drives the dashboard and this page in Google Chrome. The full list is in TESTING.md.
